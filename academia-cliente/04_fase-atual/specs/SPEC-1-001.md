# SPEC-1-001 — Ambiente Supabase reproduzível e auditável

**Fase:** 1
**Status:** planejada
**Dono:** Consultoria (implementação) · Champion valida demonstração
**Origem no escopo:** DEC-01, DEC-09, DEC-10; Fase 1 (§18); REQ-F1-01 da matriz
**Degrau da solução:** nativo da plataforma — Supabase já provê migrations, Auth, RLS e Vault; construção mínima de configuração e seed

## Resultado observável

Um projeto Supabase no qual `supabase db reset` recria o banco inteiro a partir de migrations versionadas + seed sintético, sem nenhum dado real, com segredos apenas no Vault e trilha de auditoria pronta para receber eventos. É a fundação sobre a qual todas as demais SPECs da Fase 1 são construídas e demonstradas.

## Limites e dependências

- **Inclui:** estrutura inicial do projeto Supabase (migrations, seed, ambientes), tabela de auditoria append-only, tabela de filas duráveis `queue_jobs` com dead-letter, configuração de Vault/segredos, fixture sintética de leads (sem PII real).
- **Fora de escopo:** canal WhatsApp real (F2), dados reais do Kommo (F3), agentes de IA (F4), qualquer integração externa.
- **Entradas e pré-condições:** escopo definitivo aprovado (DEC-EXEC-03); conta Supabase disponível; GATE-09 (LGPD) aberto formalmente — dado real continua proibido.
- **Saídas/artefatos:** repositório com `supabase/migrations/`, `supabase/seed.sql`, `supabase/config.toml`, README de bootstrap.
- **Dependências e responsáveis:** consultoria executa; champion acessa projeto Supabase compartilhado.
- **Risco e plano B:** limite do plano gratuito → projeto dedicado de staging; migração de projeto documentada.
- **Rollback ou reversão:** `supabase db reset` recria tudo; migrations são imutáveis após aplicadas (nova migration corrige).

## Fluxo e regras

1. Colaborador clona o repositório e roda `supabase start` + `supabase db reset`.
2. O banco sobe vazio, aplica migrations em ordem e carrega seed sintético.
3. `supabase db diff` não mostra divergência entre estado local e migrations.

| Cenário | Dado/condição | Resultado esperado | Caminho de erro/recuperação |
|---|---|---|---|
| Principal | Reset em máquina nova | Banco recriado idêntico ao da consultoria | README cobre pré-requisitos (Docker, CLI) |
| Limite | Reset duas vezes seguidas | Segundo reset idêntico ao primeiro (idempotência) | Seed usa `on conflict do nothing` |
| Falha | Migration com erro de sintaxe | Reset falha com erro claro apontando o arquivo | Migration corrigida em novo commit (nunca editar aplicada) |

## Checklist de execução

- [ ] Migrations iniciais aplicadas (auditoria, filas, extensões)
- [ ] Seed sintético sem PII real

- [ ] README de bootstrap testado em clone limpo

## Critérios de aceite

- [ ] **CA-1-01:** `supabase db reset` em clone limpo recria o banco completo sem erro manual.
- [ ] **CA-1-02:** segundo `db reset` seguido produz estado idêntico (idempotência do seed).
- [ ] **CA-1-03:** nenhuma credencial/token aparece no código, config ou seed (busca automatizada).
- [ ] **CA-1-04:** tabela `audit_log` é append-only (UPDATE/DELETE bloqueados por policy).
- [ ] **CA-1-05:** tabela `queue_jobs` aceita inserção, consome e move falha exausta para `dead_letter_jobs`.
